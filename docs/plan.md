Written on Friday, October 9, 2026, by the planning session (Fable 5.1), for the owner. It is a proposal: the owner adopts it, or parts of it, and the orchestrator applies it to the task log. Nothing in it starts until the owner says go. Every date and weekday in it was computed from the machine's clock.

What it is built on: the Worker 5.4.0 source at `D:\worker-5.4.0` (GPL-2.0-or-later) and its documentation; the owner's wiki, above all the textweaver hub, its wave planning pages, the Research Agent Rules and the Wave 4 orchestration plan; the textweaver repository's conventions (`CLAUDE.md`, the shared preamble in the planning repository, the guard, `safe-remove.ps1`, the build profiles, the Docker setup, ADRs 0027, 0043 and 0045); abax's earlier Worker-style file manager; and today's measurements of this machine. The two surveys that fed it are in the planning repository: `research/worker-survey.md` (Worker's architecture, read-only, with file and line citations) and `research/textweaver-method.md` (the textweaver method).

## The short version

- **What it is.** A two-panel file manager in pure Rust, in the orthodox style of Worker and Directory Opus, built accessibility-first for the owner's screen readers and Braille display, with a terminal frontend, a window frontend on AccessKit, and a plugin system that takes bash, Python and Lua.
- **License.** Apache-2.0 OR MIT, the Rust convention, decided by the owner on Friday, October 9, 2026 (question 2). Worker is GPL-2.0-or-later, so this is a reimplementation of its behavior, never a port of its code. The clean-room rule in section 3 keeps that true.
- **Name.** The project and the repository are diroxide, "Directory Oxide", matching the domain `diroxide.app`. The short command cannot be `do`: `do` is a reserved word in sh, bash, zsh and PowerShell, so typing it at a prompt is a syntax error. The binary is `diro`, decided by the owner on Friday, October 9, 2026 (question 1).
- **The website.** `diroxide.app`, bought by the owner on Friday, October 9, 2026: a small project site in the shape of carta.rs (one landing page and the guides, no JavaScript), built the way kd7swh.com is built (Eleventy, the whole toolchain in Docker, GitHub Pages), after the final alpha and before beta.1 (the owner's decision, Saturday, October 10, 2026). Section 8 has the design and section 9 the wave.
- **Shape.** One app core that holds all state and returns effects; three frontends over it: the terminal reader on ratatui, the window on Masonry and AccessKit (the stack textweaver already carries), and a headless JSON-RPC server for scripts and tests. The same list model, menu model and keymap serve all three, as textweaver's do.
- **Plugins.** Process plugins over JSON-RPC 2.0 on standard input and output, in any language; "script commands" for one-file bash and Python scripts with no protocol code at all; an optional in-process Lua tier for the fastest hooks; a transport designed so WebAssembly can be added later without changing the plugin API.
- **The must-haves.** Archives in both directions: zip, 7z, tar, tar.gz, tar.xz and xz, all in pure Rust. Regex search at ripgrep speed, on names and contents. ImageMagick, FFmpeg and pandoc found and driven through one tools registry, for previews that are text first and for conversions that run as jobs. Git and GitHub through the user's own `git` and `gh` programs, as a plugin: the panel aware of the working tree, a private or public repository from a folder or the marked files in a few steps, files posted as a gist, pull requests, issues, runs and releases as lists (the owner, Sunday, October 11, 2026; section 5.16).
- **The alphas.** Nine (the owner's decision, Saturday, October 10, 2026), each carrying a large number of commits: two panels (alpha.1); archives and the viewer (alpha.2); search, filters, labels, bookmarks and saved searches (alpha.3); the plugin protocol, script commands and the Lua tier (alpha.4); SSH and remote places (alpha.5); the window (alpha.6); tools, previews, conversions and git (alpha.7); tabs, flat view, collections, compare and synchronize, duplicates, batch rename, volumes and GitHub (alpha.8); and the feature-complete final alpha (alpha.9). The split from alpha.2 on is provisional until the feature catalog (R6) lands. The website is built after alpha.9 and before beta.1. The final alpha is what most projects call 1.0.
- **The method.** The textweaver method, unchanged where it worked: a Phase 0 contract first, waves of three to five building agents in their own worktrees with crate ownership, one app-wiring agent per sub-wave, batch merges, CI watched by run id, the guard and `safe-remove.ps1`, dates from the clock, and the owner's sessions as follow-ups rather than gates. Fable plans, Opus builds, Sonnet researches and writes prose, Haiku watches.
- **Pace.** The owner's decision (Friday, October 9, 2026): a secondary project at about a quarter of textweaver's pace. textweaver went from an empty folder to a feature-complete alpha in two weeks with up to five builders at a time; diroxide runs one or two builders at a time and waits for the owner's check between waves, so the final alpha is a matter of months, not weeks. Nothing here is a promise or a date.
- **Twelve questions** for the owner are in section 13, each with a default so that a "go" alone is enough to start.

## 1. What diroxide is

### The pitch

An orthodox file manager: two panels side by side, one active, one the target. Everything is a command, every command has a key, a name in the palette and a place in the menus, and every command can be bound to a button in a bank, as Worker's can. It is fast because it is Rust and because it never blocks the interface: listing, searching, copying and archiving run as jobs that report progress in words. It is safe because the owner's own rules from September 26, 2026 are built into the product (section 5.12). It is modern because it runs on Wayland, Windows and macOS through winit with no X11 code, and because the things Worker left to Lua are open to any language.

### Who it is for

The owner first: blind, reading through JAWS and NVDA and a 40-cell HumanWare Mantis Q40, and red-green color-blind. Every row of a panel puts its meaning in the first 40 cells. Status is words, never a symbol or a color. Then power users who want Worker or Directory Opus without X11 and without a proprietary license.

### Names

- **Project and repository:** diroxide, "Directory Oxide". The repository is `diroxide`, matching the domain `diroxide.app` (the owner, Friday, October 9, 2026). The crates are `diroxide-*` and the config folder is `diroxide`, as textweaver names its crates and its folder after the project and its binary `tw`. Lowercase everywhere.
- **Folders:** `D:\diroxide`, with the planning repository at `D:\diroxide-planning`. Unchanged.
- **Command:** `diro`. The owner suggested `do`, which is a reserved word in every shell the project targets (`for ... do ... done` in sh, bash and zsh; `do { } while` in PowerShell), so a binary named `do` cannot be run by typing its name. `diro` is four letters, reads as one word in speech, and is free on PATH on all three platforms. The binary crate is `diro`, so `cargo install diro` is the install line once it is published. (Decided, question 1.)
- **Config folder:** `diroxide` under the platform's config directory (`%APPDATA%\diroxide`, `~/.config/diroxide`, `~/Library/Application Support/diroxide`).
- **Domain:** `diroxide.app`, bought by the owner on Friday, October 9, 2026. The website is in section 8.

### License

Apache-2.0 OR MIT, dual, as Rust crates are. Every dependency in section 6 is compatible. `cargo deny` enforces the allow-list from the first commit. The copyright line follows textweaver's precedent: the owner's name in `NOTICE`, the README and `diro --version`; "the owner" everywhere else. (Question 2.)

### The icon

Chosen on Saturday, October 10, 2026: a friendly orange crab sitting on the open top drawer of a rusty steel-blue filing cabinet seen in three-quarter view, waving one claw; cel-shaded, flat fills with one hard shade step and ink outlines, no gradients; rust orange on steel blue, a color-blind-safe pair, no red or green; no text in the mark. The mark (a 32-unit drawing that reads at 16 pixels), the full illustration and the wordmark ("diroxide" in drawn rounded letters, "dir" blue and "oxide" orange, with the tagline "Directory Oxide: a modern Rust file manager") are in `assets/logo/` with their alt text; the designer's other concepts and full descriptions are in the planning repository. The window alpha rasterizes the mark with `cargo xtask icons` (resvg, pure Rust) into PNG at 16 to 512 pixels, a Windows `.ico`, a macOS `.icns` and a Linux `.desktop` icon. Nothing has been rendered yet; a sighted review or a raster render precedes the first release that ships the icon.

## 2. What Worker does, and what carries over

The Worker survey (`research/worker-survey.md` in the planning repository, Friday, October 9, 2026, read-only, with file and line citations) replaced the planning session's guesses. Worker 5.4.0 is dated March 1, 2026, and its first release was in March 1999. It is about 176,000 hand-written lines of C++17, plus 17,000 generated by bison, flex and Ragel; 35,000 of the hand-written lines are AGUIX, the author's own X11 toolkit. Two thirds to three quarters of the code is entangled with that toolkit, and even the copy command carries its own dialog. The survey's conclusion: a clean split of core and frontend is a redesign, not a port, which is what the clean-room rule requires anyway.

### How Worker is built

- One application object owns the window, the button, hotkey and path tables, the status and clock bars, and two listers; a select loop over the X connection, timers and child exits drives it.
- A lister hosts one mode at a time: the file list, an image view, an information view or the text view. Modes register named string commands.
- The file list mode (10,000 lines) holds tabs, a directory cache of 50 entries, filters, sorting, selection, breadcrumbs, an info line, free space and an inotify watch.
- Entries form a small tree of types: entry, directory, file and virtual directory. A virtual directory is any list of paths, and it is the universal result type: search results, flattened trees, the selection as a list, a command's output, path jump results, directory compare results and clipboard paste all become one.
- One visitor interface walks directories for copy, delete, search and dirsize. Copy runs on its own thread with several overwrite policies and background copies; delete unlinks directly; trash is a script in the default configuration that calls `gio trash`.
- Sixty command classes, each with a run method and its own configuration dialog, in eight categories (file type actions, cursor, file list, file operations, selections, settings, scripting, other), plus about forty-five string commands reachable from scripts.
- File type checking, directory reading, search, copy and the path store run on threads; the interface stays on one.
- Configuration is a hand-editable text file with its own grammar (a 1,862-line bison parser and 230 keywords), with sections for global settings, colors, startup, fonts, clock bar sets, path buttons, 41 hotkeys, 157 buttons in banks on a four by seven grid, and 144 file types. Keys are X keysyms with X modifier names.

### Carried over as features

Everything in this list is in Worker today and becomes a diroxide feature, in the alpha noted.

- Two panels, one active, Tab between them, each with tabs, tab lock and saved tab profiles (alpha.1; tabs in alpha.6).
- Columns: name, size, human size, type, permissions, owner, link destination, modified, accessed, changed, inode, links, blocks, extension and a custom attribute (alpha.1).
- Buttons in banks, switched by a command, each running a list of commands (alpha.1).
- One key table for buttons, hotkeys and path buttons; single keys and Emacs-style two-key chords with the continuations shown in the status line; a help mode that explains a key; unmatched keys as type-ahead filtering (alpha.1).
- Sixty commands as the unit of configuration: copy (also move, rename and duplicate), delete, rename, make directory, chmod, chown, chtime, create and change symlink, dirsize, reload, directory compare, clipboard; enter directory, enter path, path to the other side, path jump, bookmarks, directory cache, newest files, external virtual directory; change columns, hidden flag, layout, lister set, sort mode, filter, search entry, filter select and unselect, scroll, toggle mode, switch lister, tabs, tab profiles, label; own command, start program, script, internal view, text view, search; switch bank, shortkey from list, command menu, context menu, menu, volume manager, help, command log (alpha.1 to alpha.6, as their areas land).
- The flag language of "own commands": `{f}` the name, `{F}` the full path, `{a}` and `{A}` all selected, `{p}` the path, `{lp}` and `{rp}` the left and right paths, `{op}` the other path, with escaped, unquoted and other-side variants, plus a prompt, stack access, size, environment, current time and random. diroxide keeps these as the placeholders of script commands (alpha.3).
- Start modes for commands: normal, in a terminal, in a terminal that waits, with output shown, output shown to the other side, or output stored as a custom attribute (alpha.3).
- File types as a tree with subtypes and priority; detection by a 64-byte magic signature with wildcards or libmagic, then an extended condition (size, permissions, name, content at an offset, link state), then a name pattern (fnmatch, comma list or regex); checked in the background with "not yet checked" shown until the result arrives; per-directory "don't check" for slow mounts; actions per type for drop, double-click, show, raw show, ten user actions and named context-menu actions (alpha.5).
- Path jump with learned ranking (a prefix database with aging), by time, by filter or by program, with results as a virtual directory; bookmarks with categories, aliases, sticky entries and a bookmark-only filter; directory history and a previous-directory key; breadcrumbs; per-directory sort and filter presets (alpha.2 and alpha.6).
- Filter expressions per lister over name, size, type, state, access time, modification time and content, with a fuzzy operator; type-ahead filtering; stashed filters (alpha.2).
- Search by name (fnmatch or regex, comma-separated, full path) and by content (regex, case, byte limit, line numbers), with follow symlinks, search inside archives, one filesystem, exclude by label, age and size bounds, a match expression, histories and a result preview (alpha.2).
- Dirsize into the size column (alpha.2; in diroxide a job, not a synchronous walk).
- The text view: wrap, line numbers, jump to line, reload, follow and watch a file, command output, smart-case regex search (alpha.2).
- Directory compare by name, size, date, content or checksum, and a newest-files view (alpha.6).
- Labels with colors, in diroxide words first (alpha.2).
- The volume manager through udisks2 over D-Bus, falling back to fstab and mtab with configurable mount, unmount and eject commands (alpha.6, through a plugin).
- Clipboard exchange with other file managers (`text/uri-list` and GNOME's copied-files form), drag and drop, a command log, hint tips, and eleven translations (the window in alpha.4; translations after the final alpha if wanted).

### Changed on purpose

- **Every operation is a job.** Worker's dirsize and delete are synchronous and its copy is threaded. diroxide runs all of them through one engine with plans, progress in words, cancel and undo.
- **The trash is the default,** and permanent delete is its own listed command. Worker unlinks and leaves the trash to a script.
- **Space selects, not Insert.** Insert is the NVDA and JAWS key. Worker's keypad plus, minus, star and slash for select all, none, invert and by pattern stay, with letter equivalents for laptops.
- **A hex mode in the viewer.** Worker has none; it shows non-printable bytes as escapes and leaves hex to an external editor.
- **Archives in pure Rust, both directions.** Worker reads archives through AVFS (`#utar`, `#uzip`, `#u7z` and the rest) and writes them with external packers. diroxide's provider reads and writes zip, 7z, tar, tar.gz, tar.xz and xz in-process; the member path form `archive.zip!member` replaces Worker's `#` suffix.
- **A regex crate, not POSIX.** Worker uses `regcomp` with an extended-syntax switch; diroxide uses Rust's `regex` everywhere, with the same syntax in filters, search and rename.
- **TOML, not a grammar.** Worker's parser and keywords become `config.toml`, `keymap.toml`, `filetypes.toml` and `banks.toml`, with a schema that generates the reference page; Worker's 8,600 lines of configuration dialogs become the Settings list.
- **No shell in built-in operations.** Worker runs every external command as a temporary shell script through `xterm -e /bin/sh`. diroxide runs tools with argument lists and opens a terminal only for commands that ask for one.
- **The plugin protocol replaces Worker's scripting.** The survey's most useful correction: Worker's Lua is 223 lines that only compute the info line under the list (eight variables, no API, no callbacks). Its real scripting is the stack-based script command (push, pop, label, if, goto, settings, window, evaluate), the flag language and the string commands, which the default configuration uses for batch rename, trash and case conversion. diroxide keeps the flags as placeholders, replaces the stack scripts with script commands in any language, and makes Lua one in-process tier among several.
- **Pure-Rust file type detection** with the same three-stage model (magic, condition, pattern) and the same background checking, with libmagic as an optional plugin rather than a build dependency.
- **The window on AccessKit** instead of AGUIX: real list, grid, menu and dialog roles, so a screen reader reads a panel as a table rather than as drawn text.

### Added from Directory Opus

- Flat view as a lister mode (Worker's `flatten_dir` exists as a string command; diroxide makes it a mode with the relative path in a column).
- Collections: Worker's virtual directories made persistent and nameable, so a search result or a hand-picked set survives a restart.
- Synchronize from a compare, with a plan the owner reads before anything is copied.
- Duplicates by size, hash and comparison.
- Batch rename with a regex and a preview of every old and new name (Worker's is a script with no preview).
- A details view that says what a file is, text first (Worker's information mode and info line, extended with the tools of section 5.9).
- The same commands from a shell through `diro`.

### Dropped or replaced

- AGUIX and every X11 call (XDND, X selections, XIM, Xinerama, Xft, imlib2): replaced by ratatui in the terminal and by Masonry, winit, Vello and AccessKit in the window.
- The configuration grammar and its dialogs: replaced by TOML and the Settings list.
- AVFS and its FTP module: replaced by the archive and SFTP providers.
- libmagic, HAL and uDisks as build dependencies: replaced by pure-Rust detection and a plugin for mounting.
- autotools: replaced by Cargo, xtask and the release workflow.
- The image mode on imlib2: the window renders images through the `image` crate, and the details view describes them in words.
- POSIX-only calls (fork and exec, waitpid, chown, mkfifo, statvfs, inotify, getpwuid): behind the local provider's platform module, with Windows equivalents.

### What the survey could not verify

The online manual is not in the tarball, so the meaning of "raw show", the mouse defaults and the button bank arithmetic are inferred from code and configuration; AVFS's internals and the `cd2*.sh` helper scripts were not read; nothing was built or run. The R1 inventory in Wave 0 closes these with the manual.

## 3. The clean-room rule

Worker's code is GPL-2.0-or-later. diroxide is Apache-2.0 OR MIT. A port of Worker's code would be a derivative work and could not carry that license. So:

1. **Two roles, never one agent.** Research agents (Sonnet) read Worker's source and documentation and write specifications: what a feature does, its inputs, outputs, keys, edge cases and defaults, in their own words, with file and line citations for the orchestrator's verification. Building agents (Opus) never read Worker's source; they build from the specifications and from the public documentation.
2. **No Worker code, names of internal types, comments or configuration snippets** go into the repository. Default key bindings and user-facing behavior are not copyrightable and may match.
3. **Every brief says which role it is.** A building agent's brief does not name `D:\worker-5.4.0` and forbids reading it; the guard allows reads there (research agents need them) and denies every write or delete there. At integration the orchestrator runs `git grep` over the branch for Worker's internal names (`aguix`, `virtualdirmode`, `FunctionProto`, `NWC`, `wconfig`) and refuses a merge that contains one.
4. **The owner's own code is different.** textweaver is GPL-3.0-or-later, but the owner holds its copyright, so the owner may release any of it under Apache-2.0 OR MIT for diroxide. The pieces worth carrying over are named in section 7. The orchestrator confirms with the owner that no third party holds copyright in those pieces before they move (question 3).
5. **The records say so.** `docs/dev/clean-room.md` records the rule and the list of specifications; `THIRD-PARTY-NOTICES.md` is generated by `cargo about` as in textweaver.

## 4. Design principles

1. **Accessibility first.** A row says its meaning in the first 40 cells; status is words; color never carries meaning alone; every control has a name and a role; every change is announced; everything works from the keyboard. If an accessible way is not possible, the report says so; nothing inaccessible ships quietly.
2. **One app core, many frontends.** The core holds every panel, job and dialog and returns effects; frontends draw and announce. A feature exists when the core has it; a frontend only shows it. Tests drive the core without a terminal or a window.
3. **Everything is a command.** A command has an id, a name, a key, a menu place and a palette entry, from one model. Buttons, plugins and `diro` call the same commands.
4. **Never block the input thread.** Listing, stat, search, copy, archive and preview run on worker threads or the async runtime; the core receives messages. A slow network share pauses one job, not the program.
5. **Pure Rust first, tools second, and anything that is not Rust stays optional** (the owner, Saturday, October 10, 2026). Archives, search, detection, images and SSH are in-process Rust. ImageMagick, FFmpeg, pandoc, the 7z tool, ExifTool, pdfinfo and gpg are found and used when present, never required. The `diro` binary and every crate it links contain only Rust and build with no C compiler; there are no feature flags that pull C in. Crates that carry C, C++ or assembly inside (the ring or aws-lc-rs cryptography that russh needs, the AVIF, HEIC and raw decoders, Lua through mlua, tree-sitter), and libraries whose licenses the main binary cannot carry, are approved by the owner for plugins only (Sunday, October 11, 2026): separate executables in their own workspaces under `plugins/`, which a user opts into with `cargo install` of the plugin's crate or through the optional-components downloader, in the way textweaver's components chooser works; where a pure-Rust alternative exists it is preferred in the main binary. `cargo deny` and a build-tree check over the main workspace in CI enforce it. The owner's textweaver spirit applies: push the envelope with Rust, accept alpha crates, keep the gates, record each bold choice and its fallback in an ADR.
6. **Safe by construction.** Built-in operations never go through a shell. Paths are literal. Deletes list what they will remove. The trash is the default. Confirmations default to No. See section 5.12.
7. **Plain configuration.** TOML files a person can read and diff, unknown keys preserved, atomic writes, a schema that generates the reference page.
8. **Measure, then optimize.** A bench gate from alpha.1 (list 100,000 entries, search a 1 GB tree, copy 10 GB) fails in both directions, as textweaver's does.
9. **Lean.** No crate for a few lines. No option nobody asked for. The smallest complete change ("Ponytail", from the textweaver beta brief).
10. **US English, no feature numbers in user docs, em dashes sparingly, dates from the clock.**

## 5. Architecture

### 5.1 The workspace

One Cargo workspace, edition 2024, resolver 3, toolchain pinned to 1.96 (the toolchain in the project's rustup home, shared with textweaver; repinned from 1.98.1 at the Phase 0 integration), `[workspace.dependencies]` declared once, one crate per job, dependency direction checked by `cargo xtask deps --check`:

- `diroxide-core`: ids, errors, `Place` and `Entry`, the list model, commands and effects, messages and announcement kinds, the clock trait. No I/O.
- `diroxide-vfs`: the `Provider` trait, places, capabilities, cancellation, the registry, and the local provider.
- `diroxide-archive`: the archive provider for zip, 7z, tar, tar.gz, tar.xz and xz, reading and writing, with limits.
- `diroxide-sftp`: the SFTP provider on russh.
- `diroxide-ops`: the job engine: copy, move, delete, rename, make directory, links, attributes, times, trash, conflicts, progress, undo log.
- `diroxide-search`: name and content search, dirsize, duplicates, results as a lister.
- `diroxide-filetype`: detection and the file-type registry with actions.
- `diroxide-config`: settings, keymap, file types, banks and plugins configuration, in TOML.
- `diroxide-plugins`: the protocol types, the host, script commands, and the Lua tier behind a feature.
- `diroxide-tools`: the external tools registry (ImageMagick, FFmpeg, pandoc, and others), detection and safe running.
- `diroxide-preview`: previewers, text first, over tools and pure-Rust readers.
- `diroxide-app`: the app core: two panels, tabs, commands, keymap dispatch, menus, palette, dialogs, jobs, announcements.
- `diroxide-tui`: the terminal frontend on ratatui and crossterm.
- `diroxide-gui`: the window on Masonry and AccessKit.
- `diroxide-cli`: the `diro` binary: open, serve, search, convert, plugin tooling.
- `xtask`: deps, regen, keyboard, settings reference, notices, icons, dist, bench.

Sixteen crates. textweaver reached 36; a file manager needs fewer. A crate is added only when a wave's brief says so.

### 5.2 The core model

- **Place.** A location any provider can serve, written as a path with an optional scheme: `D:\photos`, `/home/owner`, `course.zip!week1/` (an archive member path, the form textweaver and star use, so nothing is extracted to browse), `sftp://host/path`. A place has a display form that says its kind first in the title line ("week1, in course.zip").
- **Entry.** Name, kind (folder, file, link, archive, special), size, times, mode or attributes, owner, link target, labels, and a display name with control, format and direction characters replaced by a question mark (the real name is kept for operations).
- **Lister.** A place, its entries, sort, filter, columns, selection, cursor, history, and the tab it belongs to. Two listers are live; one is active.
- **The list model.** One list type, with its title, rows, focus, letter jump, Home and End, F1 help, Say Status, and position said last ("report.pdf, PDF, 2.1 MB, modified Tuesday, 3 of 40"). It is the same shape as textweaver's `ListModel` (ADR-0045), reused here for panels, search results, bookmarks, jobs, menus and every chooser, so every list reads the same way.
- **Commands and effects.** `Command` ids with arguments; `dispatch` returns `Effect`s (redraw, announce, open dialog, start job, run plugin). Frontends execute effects.

### 5.3 The virtual file system

A `Provider` trait with `list`, `stat`, `read`, `write`, `create_dir`, `rename`, `remove`, `set_attributes`, `copy_hint` (for same-provider fast paths), `watch` (optional), each taking a cancellation token and reporting progress; a `Capabilities` set (writable, trash, links, attributes, case-sensitive, max name length, reserved names); and a registry that resolves a place to a provider. Providers:

- **Local** (in `diroxide-vfs`): `std::fs` with platform details behind a small `sys` module: Windows attributes, long paths, reparse points, drive listing from `GetLogicalDrives` (never touching the drive, as textweaver's browser does); Unix modes, owners and groups; macOS resource forks ignored.
- **Archive** (`diroxide-archive`): zip through the `zip` crate (deflate, bzip2, zstd, lzma and xz entries), 7z through `sevenz-rust2` (LZMA, LZMA2, BZIP2, PPMd, with writing), tar and its gzip and xz wrappers through `tar`, `flate2` and `liblzma` or `lzma-rust2` (question 6), plain `.xz` as a one-member archive. Reading lists and reads members in place; writing packs a selection into a new archive or adds to one, as a job with progress. Limits from textweaver's archive module: member size, bytes decompressed, 7z dictionary size, entry count, nesting depth of four, normalized names so a member called `../../x` cannot leave the archive, junk entries hidden.
- **SFTP** (`diroxide-sftp`): russh and russh-sftp, key and agent authentication, known hosts checked, a connection per host kept open, listings and transfers streamed. Password entry goes through the frontends' prompt, never a command line.
- **Plugin providers** (section 5.8): S3, WebDAV, MTP and anything else, served by a process plugin that implements the provider methods.

### 5.4 The job engine

Every operation that touches more than one entry, or that can take more than a moment, is a job in `diroxide-ops`: a plan (what will happen, computed first and shown on request), a queue, progress in words ("copying 12 of 300, 1.2 of 4.0 GB, about two minutes left"), pause, cancel, a conflict policy asked once per job (ask, skip, overwrite, keep both, rename), and a result list (done, skipped, failed, with reasons). Copy preserves times and attributes, uses reflinks or server-side copy where the provider offers them, and moves within one provider by rename. Delete goes to the trash through the `trash` crate; permanent delete is a separate command that lists every path first. Renames and moves are recorded in an undo log that the Undo command replays for the last job. Nothing in the engine runs a shell.

### 5.5 Search

`diroxide-search` uses ripgrep's own crates: `ignore` for the parallel walker (with gitignore rules optional), `globset` for name patterns, `grep-regex` and `grep-searcher` for contents, so a content search runs at ripgrep's speed in-process. Filters: name glob or regex, content regex, size, dates, kind, depth, hidden. Results arrive as they are found into a results lister that every command can act on (copy, move, open, collect), and the search can be saved as a collection or a filter. Dirsize walks with the same walker but with its filters off, since the crate's default filters skip hidden and ignored files and would undercount (R14); a skipped entry is counted in a summary line. Duplicates by size, then by a fast hash (`blake3`), then by full comparison for the hits.

### 5.6 File types and actions

Detection in `diroxide-filetype`: extension first, then magic bytes through `infer` and diroxide's own table (text, scripts, archives, documents), then an optional content check. Types are in `filetypes.toml`, user-extendable, with a priority order and actions: open (the default), view, preview, convert, and user actions, each a command or a plugin call. Actions that run a program use the tools registry (section 5.9), never a shell string.

### 5.8 The plugin system

The owner wants to automate file management in bash and Python before Lua, and to reach other protocols such as SSH. So the plugin system is a protocol, not a language.

**Tiers.**

1. **Process plugins.** A plugin is a folder with a `plugin.toml` manifest and a program in any language. diroxide starts it on demand and talks JSON-RPC 2.0 over its standard input and output, one JSON object per line, UTF-8, in both directions. The manifest names what the plugin provides: commands (with names, descriptions and default keys), file-type actions, providers (the methods of section 5.3), previewers, converters, and hooks (before and after copy, delete, rename, enter folder, select). The host offers the plugin: `ui/announce`, `ui/ask` (yes or no, choose from a list, prompt for text or a path, all through the frontends' accessible dialogs), `ui/progress`, `panel/get` and `panel/set` (place, selection, cursor, refresh), `fs/*` (list, read, write, copy, move, delete through the job engine, so a plugin's operations get the same safety, trash, progress and undo as built-in ones), `tools/run` (run a registered tool), `config/get`, and `log`. The plugin answers `initialize`, `command/run`, `provider/*`, `preview/render`, `convert/run`, `hook/event` and `shutdown`. The owner can write one in Python with the standard library alone: read a line, `json.loads`, answer. Reference plugins ship in `examples/plugins/` in bash, Python and Lua, and `diro plugin new --language python` writes a working skeleton.
2. **Script commands.** No protocol at all. A one-file script in `plugins/scripts/` with a header comment (`# diro: name = "Make thumbnails"`, `# diro: key = "ctrl+alt+t"`) becomes a command. diroxide runs it with the context in environment variables (`DIRO_ACTIVE`, `DIRO_OTHER`, `DIRO_CURSOR`, `DIRO_SELECTION_FILE` naming a file with one selected path per line) and as JSON on standard input. Standard output goes to the output pane, except lines that start with `diro:`, which are directives: `diro:announce ...`, `diro:refresh`, `diro:cd PATH`, `diro:select PATH`, `diro:progress N of M`. The exit code is the status. Worker-style one-line commands with placeholders (`{file}`, `{files}`, `{dir}`, `{other}`, `{dest}`) are the smallest script command; abax did the same in Python.
3. **The plugin boundary is the language boundary** (the owner, Sunday, October 11, 2026). The `diro` binary and every crate it links are pure Rust and build with no C compiler. Anything that needs C, assembly, another language or a license the main binary cannot carry lives in a plugin executable that the user opts into: the SFTP provider (its cryptography is C-backed), the extended previewer (the AVIF, HEIC and camera-raw decoders are AGPL, LGPL or C), the encryption plugin (OpenPGP through an LGPL library, or gpg), tree-sitter highlighting, structural diffs, a Lua runner for Lua scripts, and whatever else arrives. A plugin is a separate process, so a copyleft library inside it never touches the main binary's license. The plugin crates live in a `plugins/` folder of their own workspaces, excluded from the main one, so `cargo build --workspace` and `cargo install diro` never see a C dependency; each plugin is installed with `cargo install` of its own crate or as an optional component (section 5.14). The in-process Lua tier is retired: Lua scripts run through the Lua runner plugin like any other language, and the column formatters and per-row filters it was meant for are served by the batched `column/format` request, measured before anything faster is considered. A plugin need not carry C to be one: the git and GitHub plugin of section 5.16 is pure Rust and is a plugin because it is a whole feature family that not every user wants, and because it is the reference plugin in Rust.
4. **WebAssembly.** Not in the first alpha. The host's transport is a trait (`PluginTransport`: stdio process today), so a component on wasmtime, or an Extism plugin, can be added as a second transport without changing the plugin API. Recorded as the fallback in the ADR.

**Why not embed Python.** PyO3 ties the binary to one Python version and makes a plugin crash a diroxide crash. A process plugin uses whichever Python the owner has, is isolated, and matches how the owner already works.

**Safety.** A plugin runs with the user's rights, so the manifest's capability list is shown on first enable and nothing is enabled by default. A plugin crash or timeout is reported and the app continues. `--no-plugins` starts clean. Plugins never receive a shell string; `tools/run` takes an argument list. Each plugin has its own log in the state folder.

**Why this works for SSH.** SSH is built in through `diroxide-sftp` because the owner needs it from the start. The provider protocol lets the same thing be done by a Python plugin with paramiko for a protocol diroxide does not carry.

### 5.9 Previews, tools and conversions

**The tools registry** (`diroxide-tools`): one table of external programs (`magick` and `convert`, `ffmpeg` and `ffprobe`, `pandoc`, `7z`, `pdftotext`, `xdg-open` and its platform equivalents), each with how to find it (PATH through one lookup rule, then `tools.toml` overrides), how to read its version, and how to run it: an argument list, no shell, no console window on Windows, output captured, cancellable. ### 5.12 Safety, built in

The owner lost most of a user profile on September 26, 2026 to a delete that read a hidden character as a drive letter. A file manager is the one program whose whole job is such operations, so the rules become features:

- **Every delete, move and overwrite lists what it will touch first,** with hidden, control, private-use and direction characters spelled out as `U+XXXX` and the count said in words. The confirmation starts on No.
- **Paths are literal.** Nothing a user types or a plugin sends is expanded by a shell. Built-in operations use argument lists and `std::fs`.
- **The trash is the default.** Permanent delete is its own command with its own key and its own listing.
- **Dangerous names are flagged** on creation and rename: reserved characters, trailing dots and spaces, Windows device names, shell-special characters, names that differ only by case from a sibling. The row says "name needs care" in words.
- **Boundaries are respected.** A recursive operation never follows a symbolic link or junction out of its root; an archive member never writes outside its destination folder.
- **Undo** replays the last job's renames and moves; a delete to the trash is undone by restoring from it.
- **Nothing escapes a drive letter.** A path such as `C:` without a slash is refused as ambiguous; the app always resolves to a full path before acting and shows it.

### 5.14 Optional components

Everything that is not in the default build is an optional component, fetched on request the way textweaver's are (the owner, Saturday, October 10, 2026, 11:06 PM), with textweaver's components crate and its guide as the model, relicensed under answer 3.

- **What a component is.** A helper program (pandoc, FFmpeg, ImageMagick, 7-Zip, ExifTool, pdfinfo), where its publisher makes a build for the user's computer; a plugin executable from the `plugins/` workspaces, which is where everything that needs C, assembly, another language or a license the main binary cannot carry lives (the SFTP provider, the extended previewer with the AVIF, HEIC and raw decoders, the encryption plugin, tree-sitter highlighting, structural diffs, the Lua runner), and where a pure-Rust feature family that not every user wants lives too (the git and GitHub plugin of section 5.16), so that a package user opts into them by download the same way a source user opts in with `cargo install` of the plugin's crate; and a data pack (the retro file-type pack, keymap presets, a lexicon). Each has an id, a name that says what it is for, a version, a size per platform, a license and a SHA-256 per file, in one public manifest kept in the repository and published with each release.
- **Asking, never fetching on its own.** When a feature needs a component, diroxide asks at that moment, with the size and the license first: "Reading a RAR file needs 7-Zip 25.01, 3.1 MB, license LGPL-2.1-or-later. Download it now? y or n". After a yes the download runs as a job, its progress said every ten percent and never as a spinner; Escape stops it and the next attempt resumes; when it finishes the feature starts without a restart. A no is remembered until the next start, and the feature says in words what it cannot do. Where a helper has no build for the computer, the message names the command that installs it from the system's packages, for the user to copy.
- **Manage optional components.** A list under the Tools menu and the palette, each row meaning first ("7-Zip, for RAR and ISO archives: not installed, 3.1 MB, license LGPL-2.1-or-later"); Enter offers Download, Verify the files (size and SHA-256, "Files check out" or each file named), Remove (asks first, removes only the component's own files), and Install from a zip file or a folder, checked against the same pins, for a computer without a network. The first run shows the list once with nothing chosen. `diro components` does the same from a shell (list, download, verify, remove, install-from).
- **Where components come from.** A `components_source` setting names the manifest's location. The default is the public manifest and the release assets of the project. The owner keeps a private mirror of every component for their own use, named only in their own settings; it is never named in code, tests, docs, CI or any public file, as textweaver's rule has it. A source is trusted by its pins, not its address: a file whose SHA-256 does not match the manifest is refused and removed.
- **Where they live.** Under the state folder, one folder per component, never beside the binary unless `--portable` is on; every feature that uses a component finds it there through the tools registry (section 5.9) or the plugin host (section 5.8).
- **When.** The downloader, the manifest, the Manage list and `diro components` arrive in alpha.4 with the plugin host, since plugins are the first components; the SFTP provider plugin as a component in alpha.5; the helper programs in alpha.7 with the tools registry; data packs as their alphas come.

### 5.16 Git and GitHub, as a plugin

**The decision** (the owner, Sunday, October 11, 2026, 1:01 AM). Advanced git and GitHub support: diroxide looks for the `gh` command-line program, which the owner has on most systems and has already signed in, and works through it; a private or public repository is made from a folder or from the marked files in a few steps; files are posted as a gist; and the whole of it is a plugin.

**Why a plugin.** It is pure Rust and needs no C, so it could live in the main binary. It is a plugin because it is a whole feature family that a user without git never wants, because it runs two outside programs under the user's own sign-in, and because it exercises every part of the protocol at once (a provider, commands, listers, a column, hooks, dialogs and jobs), which makes it the reference plugin in Rust beside the bash and Python examples. The crate is `diro-git`, in `plugins/diro-git/` as its own workspace, installed with `cargo install diro-git` or as an optional component (section 5.14) and listed in the public manifest. The main binary knows nothing about git.

**The programs, found and never required.** `git` and `gh` are tools in the registry's sense (section 5.9): looked up by the one PATH rule, then the usual install places (GitHub CLI's folder under Program Files on Windows, Homebrew's folders on macOS, the system's binary folders on Linux), then a `tools.toml` override; the version read once, with a minimum for each (git 2.x for the machine-readable status, gh 2.x for JSON output); every call an argument list through `tools/run`, no shell, no console window on Windows, output captured, cancellable, NUL-separated wherever git offers it. The plugin's manifest names both under `needs`, so the Settings tools page lists them as found with a version or not found with how to install, in words, and a command that needs one is shown disabled with the reason ("needs gh, not found") rather than hidden. Sign-in is gh's own: the plugin reads `gh auth status` once per session to learn whether gh is signed in and to which hosts, and never asks for, stores, logs or sees a token; diroxide's configuration holds nothing about the account. When gh is signed out, the GitHub commands say "GitHub CLI is not signed in" and offer to run `gh auth login` in the user's terminal, in the foreground, where the user completes it; the plugin never automates a sign-in.

**Git in the panel.** When a place is inside a working tree (found by walking up to a `.git` folder or file, so linked worktrees and submodules count), the panel's title line says the branch and the state first, in words: "main, 2 ahead, 3 changed". A Git column, present once the plugin is installed and on by default inside a working tree, says each row's state as a word (Modified, Added, Deleted, Renamed, Untracked, Ignored, Conflict, Staged, Submodule, Clean) through the batched column request, from one machine-readable `git status` call per listing, cached until the folder's watch fires; nothing by color alone, and the window adds a marker beside the word, never instead of it. The column filters and sorts like any other.

**Git commands.** Under a Git submenu of the Plugins menu and in the palette by name ("Git: commit"); no default keys, since the owner's key rules keep the common keys for the file manager, and a user binds any of them in `keymap.toml` or the key editor. The commands:

- Status: the summary in one line (branch, upstream, ahead and behind, counts by kind), and the changed files as a lister whose rows say the state first; Enter on a row shows the file's diff.
- Stage, unstage and stage all for the marked entries; Add to .gitignore.
- Commit: a dialog with the message field first, the staged files listed in words, Amend off by default, Sign-off as a checkbox; the message goes to git on standard input, never on a command line.
- Diff of the focused file: the working tree against the index, the index against HEAD, or any two revisions. git supplies the old text and the working tree the new, and diroxide's own diff view reads them in the fixed order of R18 (the verdict line first), so a git diff sounds like every other diff in the program.
- Log for the folder or the focused file: a lister of commits, each row date and subject first and the hash last; Enter shows the commit's changes as a lister. In the viewer, "say who changed this line" reads blame for the cursor line in words.
- Branches: list, switch, create, rename; stashes: list, push, pop and drop; Fetch; Pull, fast-forward only by default; Push, never forced; Clone into this panel, as a job; Make this folder a repository (init, a `.gitignore` from a chosen template, a first commit). Linked worktrees and submodules are listed as what they are.
- Discard changes to the marked entries restores from the index after the usual listing and a confirmation that starts on No, and keeps what it discarded in a stash named with the time, so a discard can be undone.

**The rules for a destructive git command** follow section 5.12: every command that can lose work (discard, stash drop, branch delete, a reset of any kind) lists what it will touch first and starts on No; `git clean`, a hard reset and a forced push do not exist as commands; a lease-checked force push is offered once, behind a second confirmation that names the branch; nothing passes through a shell; every job reports progress in words, every ten seconds in screen-reader mode, parsed from git's progress lines.

**GitHub through gh.**

- New GitHub repository, from this folder or from the marked entries: a dialog with the name first (the folder's name, checked against the plain-name rule), visibility as a labeled choice with Private the default and Public saying "anyone on the internet can read these files", a description, the account or one of its organizations (read from gh), and, for a folder that is not yet a repository, an init, a `.gitignore` and license template and a first commit, said in words before they happen. From marked entries, the plugin copies them into a new folder in the other panel (the orthodox rule; the originals never move), makes the repository there and creates the remote. Before anything leaves the machine the plan lists what will be pushed (the file count and the size), and before a public push the plugin scans the files for names and patterns that look like secrets (`.env` files, private keys, certificate files, tokens by pattern) and says what it found; the confirmation starts on No. After the push the repository's address is said and copied to the clipboard.
- Post as a gist, from the marked files, the focused file or the viewer's selection: a dialog with the description, Secret (gh's word for unlisted) the default and Public the other choice, and the files listed with their sizes; binary files are refused with the reason, since gists hold text; the gist's address is said and copied. A My gists lister (description, visibility, file count, updated) with view, open in the browser, and delete after a confirmation.
- Repositories as a place: a `github:` scheme served by the plugin. `github:` lists the signed-in user's repositories (name, visibility in words, last updated, description) and their organizations; `github:owner/repo` lists the default branch's tree through the API, folder by folder, with sizes, and reads a file on demand, so F3 views and F5 copies from a repository into a local panel without a clone. The place is read-only ("clone to edit"), and Clone into the other panel is one command away. Open on GitHub opens the page through the safe opener.
- Pull requests, issues and runs for the repository of the active panel, each a lister with the state first ("open, draft, number 42: the title", "merged", "failed"): view, with the checks said in words and counted; check out a pull request's branch; create one from a dialog (title, body, base, draft); merge after a confirmation that names the method; issues listed, viewed, created and closed; workflow runs listed with their status in words, a failed run's log opened as text, and "watch this run" as a job that reports every ten seconds and announces the result, the way the owner watches CI by run id.
- Releases: a lister of the repository's releases; download an asset into the active panel as a job, verified against the release's checksum line when it has one; create a release from a tag after a confirmation (a release is the owner's own doing, so the command exists and asks).

**Privacy and accessibility.** The plugin makes no network calls of its own: everything goes through git and gh, which the user already trusts and which carry their own sign-in; the account name is never written into diroxide's configuration, logs or files. Every lister row puts its meaning in the first 40 cells; every state is a word, never an icon or a color alone; every dialog follows the dialogs contract with labeled fields and the default said; every long operation is a job with progress in words and Escape to cancel.

**When.** The git half (the title state, the column, status, stage and commit, diff and log, branches, stashes, fetch, pull, push, clone, init, the safety rules) arrives in alpha.7 beside the tools registry, built by the second builder of that wave in the plugin's own workspace; the GitHub half (new repository, gists, the `github:` place, pull requests, issues, runs, releases) in alpha.8. The protocol needs nothing new: providers, listers, the column request, `needs`, `tools/run` and hooks all exist by alpha.5; the one thing to confirm in the Wave 4 brief is that a lister row that is not a file (a pull request, a run) can bind Enter to a plugin command through the manifest's action binding. ## 9. The waves and the agents

### How a wave runs

The textweaver method, as it stands after Wave 9 and the beta brief:

- **Phase 0 is the contract.** The orchestrator and one Opus agent write a workspace in which every crate compiles, the core crate is finished, every owned crate has its public types with deliberately naive bodies, the ADRs are drafted, CI and Docker run, and the task log exists. Building agents keep the public signatures and replace the bodies.
- **Ownership by crate.** Each brief names the crates, binary subcommand files and fixture folders the agent owns. No one edits the core crate, the root `Cargo.toml`, the toolchain file, `.github/`, `docker/` or another agent's paths. Contract changes are written as requests in the report; the orchestrator resolves them at integration.
- **One or two builders at a time.** The owner set the pace on Friday, October 9, 2026: a secondary project at about a quarter of textweaver's pace. So a wave's briefs run two at a time, never more, plus one research or docs agent that does not build. The machine's budget (section 12) would allow more; the pace is the owner's choice, not the machine's limit. One agent per sub-wave touches the app core's messages and keys; one GUI lane at a time.
- **Worktrees and branches.** `D:\diroxide\.claude\worktrees\<id>` on `wave<N>/<letter>-<name>`, each with `CARGO_TARGET_DIR=D:/diroxide/target/<id>` and its own Docker volume. Agents never push, merge, rebase onto main or tag.
- **Integration.** The orchestrator merges in batches of three or four, the widest app change first, runs one full native and container check per batch, pushes, and watches CI by run id before calling a merge done. `cargo xtask regen` rebuilds every generated file after a merge; nothing generated is hand-merged.
- **Between waves.** `git status --short` in both repositories after every hand-back; strays removed by `safe-remove.ps1` after a dry run, the same hour, and recorded; build output flushed by the hygiene script; Docker restarted gracefully; D: and RAM checked; the task log's status lines written with clock-substituted times; the wiki updated by the orchestrator (agents never write it); a readiness page per alpha.
- **Each wave waits for the owner.** At this pace a wave ends with its readiness page and the owner's check, and the next wave starts on the owner's go, not on its own. Findings go into the next wave. Inside a wave, small reversible decisions take a recorded default. Tags, releases, new licenses, accounts, downloads outside the pre-approved list, guard changes and deletes outside the task's own output always wait for the owner.
- **Models.** Fable plans and orchestrates; Opus builds; Sonnet researches, surveys, and writes docs and prose; Haiku runs timers, CI watches and status polls.
- **Time boxes.** Every brief has one. An agent that reaches it stops and reports what is left.

## 10. Rules for every agent

The shared preamble in `D:\diroxide-planning\history\tasks.md` carries these, adapted from textweaver's; every brief points at it. In short:

- **Privacy.** No personal identifier leaves the machine or enters a file; the owner is "the owner"; the neutral User-Agent; placeholder names in test data.
- **Where to work.** `D:\diroxide`, `D:\diroxide-planning`; read-only in `D:\star\wiki`; nothing on drive C; building agents never read `D:\worker-5.4.0`.
- **Deleting.** Only through `safe-remove.ps1` after a dry run; never `rm`, `git clean` or a one-line `Remove-Item`; `git rm` of tracked files is allowed; never a delete in Bash; never an escape sequence or an odd name typed.
- **Plain names only** in anything created.
- **Ownership and the contract** as in section 9; new dependencies only from `[workspace.dependencies]`; contract change requests in the report.
- **Quality bar.** Rustdoc on every public item; `unsafe_code` denied except in named platform modules reviewed at integration; no `unwrap` or `expect` on input or I/O in libraries; `thiserror` errors; no `todo!`, `unimplemented!` or `dbg!`; accessibility is the product: every user-visible change announceable, every string readable aloud and meaningful in 40 cells.
- **Checks before reporting,** on the crates changed: `cargo fmt --all --check`, `cargo clippy -p <crate> --all-targets --all-features -- -D warnings`, `cargo nextest run -p <crate> --all-features`, `RUSTDOCFLAGS="-D warnings" cargo doc -p <crate> --no-deps`, the same in the container with the agent's own target folder, and `cargo xtask regen --check` after a settings, key or catalog change.
- **Git.** Small logical commits on the agent's branch, each ending `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`; no push, merge, rebase or tag.
- **Dates and times from the clock,** substituted in the command that writes them.
- **No scratch files** outside the worktree and target folder; `git status --short` in both repositories before reporting, listing every untracked file created, accidents included.
- **Report format.** Summary in five lines; files by crate; checks with Pass or Fail; GUI wiring needed; contract change requests; open issues; what the next wave should do first; at most five things for the owner to try with NVDA and JAWS, or "nothing to hear".
- **Research agents** follow the Research Agent Rules unchanged: one output file, a read-only shell, named folders only, pages not files, small outputs.
